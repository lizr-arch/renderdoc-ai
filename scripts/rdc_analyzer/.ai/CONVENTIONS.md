## 0. Agent 命名规则

每个 AI Agent 必须使用**自选名字 + 日期**作为标识，格式：

```
<自选名字>-<MMDD>
```

**示例**: `Echo-0119`, `Nova-0119`, `Atlas-0120`

### 0.1 命名规范

| 规则 | 说明 |
|------|------|
| 名字选择 | Agent 会话开始时自选一个易记的名字 |
| 日期后缀 | 使用当日日期（MMDD 格式） |
| 会话唯一 | 同一会话中名字保持不变 |
| 避免重名 | 检查 `locks/` 目录，避免与活跃 Agent 重名 |

### 0.2 命名流程

```
1. 会话开始
      ↓
2. 获取当前日期: py -3 -c "from datetime import datetime; print(datetime.now().strftime('%m%d'))"
      ↓
3. 选择名字（如 Echo, Nova, Atlas, Spark, Pulse 等）
      ↓
4. 组合: Echo-0119
      ↓
5. 检查 locks/ 确认无重名
      ↓
6. 在会话中固定使用此名字
```

### 0.3 名字用途

Agent 名字用于：
- 锁文件：`locks/TASK-001.lock` 中的 `claimed_by`
- 任务完成：标注是哪个 Agent 完成的
- 评分系统：区分完成者和评审者（不能自评）
- CHANGELOG：记录变更归属

### 0.4 推荐名字列表

| 名字 | 含义 |
|------|------|
| Echo | 回声 |
| Nova | 新星 |
| Atlas | 地图集 |
| Spark | 火花 |
| Pulse | 脉冲 |
| Flux | 流动 |
| Nexus | 连接点 |
| Orbit | 轨道 |

## 0.5 时间获取规范

> ⚠️ **铁律**: AI Agent 没有内置时钟，**禁止**猜测或沿用上下文中的时间

### 0.5.1 核心原则

| 原则 | 说明 |
|------|------|
| 🚫 禁止猜测 | 不得根据"常识"或"记忆"推断当前时间 |
| 🚫 禁止继承 | 不得直接复用上下文/历史消息中的时间戳 |
| ✅ 必须验证 | 每次需要时间时，必须通过系统命令获取 |
| ✅ 一次获取 | 每个会话开始时获取一次，后续复用该时间基准 |

### 0.5.2 标准获取方法

**Windows (CMD/PowerShell)**:
```cmd
echo %date% %time%
```

**跨平台 Python**（推荐）:
```bash
py -3 -c "from datetime import datetime; print(datetime.now().strftime('%Y-%m-%d %H:%M:%S'))"
```

**输出示例**: `2026-01-19 15:40:31`

### 0.5.3 会话时间基准

每个会话开始时，Agent 应：

1. **执行时间获取命令**（上述任一方法）
2. **记录为会话基准时间**
3. **后续操作基于此时间**（如 Agent ID、文件名、时间戳）

```
┌─────────────────────────────────────────────────────────┐
│ 会话开始                                                │
│    ↓                                                   │
│ py -3 -c "..."  →  获得 "2026-01-19 15:40:31"          │
│    ↓                                                   │
│ 记录: SESSION_TIME = "2026-01-19 15:40:31"             │
│    ↓                                                   │
│ Agent ID: Agent-20260119-154031                        │
│ 文件名:   tasks/2026-01-19.md                          │
│ 时间戳:   2026-01-19T15:40:31                          │
└─────────────────────────────────────────────────────────┘
```

### 0.5.4 时间格式标准

| 用途 | 格式 | 示例 |
|------|------|------|
| Agent ID | `YYYYMMDD-HHmmss` | `20260119-154031` |
| 文件名 | `YYYY-MM-DD` | `2026-01-19` |
| 文档时间戳 | `YYYY-MM-DD HH:mm` | `2026-01-19 15:40` |
| ISO 格式 (锁文件) | `YYYY-MM-DDTHH:mm:ssZ` | `2026-01-19T15:40:31Z` |
| CHANGELOG 记录 | `HH:mm` | `15:40` |

### 0.5.5 常见错误及修正

| ❌ 错误做法 | ✅ 正确做法 |
|-------------|-------------|
| 沿用压缩上下文中的 `2025-01-19` | 执行 `echo %date%` 获取真实日期 |
| 假设"今天是 2025 年" | 验证系统时钟后再使用 |
| 文件名写 `2025` 内容写 `2026` | 统一使用获取到的时间 |
| 凭记忆写"下午 3 点" | 使用 `%time%` 获取精确时间 |

### 0.5.6 时间不一致的修复

如果发现现有文件中的时间不一致（如文件名年份与内容年份不符）：

1. **获取当前真实时间**
2. **确定正确年份**（以系统时钟为准）
3. **统一修正**（文件名 + 内容）
4. **Git 提交说明**: `fix(ai): correct timestamp inconsistency`

## 1. 会话启动协议

每个 AI 会话开始时，**必须**执行以下步骤：

```
┌─────────────────────────────────────────────────┐
│ 1. 读取 .ai/INDEX.md      → 了解项目架构         │
│ 2. 读取 .ai/TASKS.md      → 查看任务状态         │
│ 3. 检查 .ai/locks/        → 确认哪些任务被锁定   │
│ 4. 向用户确认             → 明确本次会话目标     │
└─────────────────────────────────────────────────┘
```

**示例开场白**：
```
我已阅读项目索引和任务看板。当前状态：
- 待认领任务: 6 个
- 进行中任务: 0 个

请问您希望我处理哪个任务？或者有新的需求？
```

## 2. 任务认领协议

### 2.1 认领前检查

```bash
# 检查锁文件是否存在
ls .ai/locks/TASK-xxx.lock
```

- ✅ 锁文件不存在 → 可以认领
- ❌ 锁文件存在且未过期 → 不可认领，选择其他任务
- ⚠️ 锁文件存在但已过期（>2小时）→ 可以接管，需在 TASKS.md 中说明

### 2.2 认领步骤

1. **创建锁文件**:
```json
// .ai/locks/TASK-001.lock
{
  "task_id": "TASK-001",
  "claimed_by": "Agent-A",
  "session_id": "会话标识或时间戳",
  "claimed_at": "2025-01-19T15:30:00Z",
  "expires_at": "2025-01-19T17:30:00Z"
}
```

2. **更新 TASKS.md**:
   - 将任务从"待认领"移到"进行中"
   - 填写认领者、时间、预计完成时间

3. **Git 提交**:
```bash
git add .ai/locks/TASK-001.lock .ai/TASKS.md
git commit -m "chore(ai): claim TASK-001 - Pipeline 选项卡数据解析"
```

## 3. 开发过程协议

### 3.1 代码修改规则

| 规则 | 说明 |
|------|------|
| 单一职责 | 每次只修改与当前任务相关的文件 |
| 增量提交 | 每完成一个小功能点立即 commit |
| 保持兼容 | 不破坏现有功能 |
| 添加注释 | 复杂逻辑必须添加注释 |

### 3.2 代码风格

**Python**:
- 缩进: 4 空格
- 编码: UTF-8
- 行宽: 100 字符
- 命名: snake_case (函数/变量), PascalCase (类)

**提交信息** (Conventional Commits):
```
<type>(<scope>): <简短描述>

<详细说明>

<关联任务>
```

类型:
- `feat`: 新功能
- `fix`: 修复 Bug
- `refactor`: 重构
- `docs`: 文档
- `chore`: 构建/工具

**示例**:
```
feat(parser): 添加 Pipeline State 解析

- 解析 RSSetViewports 获取 Viewport 数据
- 解析 OMSetBlendState 获取混合状态
- 支持 D3D11 和 Vulkan 两种 API

Task: TASK-001
```

### 3.3 进度更新

开发过程中，每完成一个验收标准，更新 TASKS.md:

```markdown
### TASK-001: Pipeline 选项卡数据解析
- **进度**: 
  - [x] 分析 relatedCalls 结构
  - [x] 实现 viewport 解析
  - [ ] 实现 blendState 解析  ← 当前进度
  - [ ] 测试 D3D11
```

## 4. 任务完成协议

### 4.1 完成检查清单

- [ ] 所有验收标准已满足
- [ ] 代码已提交到 Git
- [ ] 运行 E2E 测试通过
- [ ] 更新相关文档

### 4.2 完成步骤

1. **最终代码提交**:
```bash
git add <修改的文件>
git commit -m "feat(xxx): 完成 TASK-001"
```

2. **更新 TASKS.md**:
   - 将任务移到"已完成"区域
   - 填写完成时间、产出、测试结果

3. **更新 CHANGELOG.md**:
```markdown
## 2025-01-19

### Agent-A (会话 xxx)
- **15:45** TASK-001: 完成 Pipeline 选项卡数据解析
  - 修改: `parse_rdc_xml.py` (+45 行), `generate_real_report.py` (+20 行)
  - Commit: `feat(parser): add pipeline state extraction`
```

4. **删除锁文件**:
```bash
rm .ai/locks/TASK-001.lock
git add -A .ai/
git commit -m "chore(ai): complete TASK-001"
```

## 5. 冲突处理协议

### 5.1 文件冲突

如果发现要修改的文件被其他任务锁定：

1. **停止修改**
2. **检查锁文件** 确认是哪个任务
3. **评估依赖** 是否需要等待
4. **通知用户** 说明冲突情况

### 5.2 任务依赖

如果任务有依赖关系：

```markdown
### TASK-004: Pipeline State 脚本集成
- **依赖**: TASK-001
```

必须等待 TASK-001 完成后才能开始 TASK-004。

### 5.3 接管过期任务

锁文件超过 2 小时视为过期，可以接管：

1. 删除旧锁文件
2. 创建新锁文件
3. 在 TASKS.md 中说明接管原因

## 8. 禁止行为

| 禁止行为 | 原因 |
|----------|------|
| ❌ 不读取 INDEX.md 直接开发 | 可能重复实现或破坏现有功能 |
| ❌ 不检查锁文件直接认领 | 导致多人同时修改同一文件 |
| ❌ 修改非任务相关文件 | 可能与其他任务冲突 |
| ❌ 不提交 Git 就完成任务 | 其他 Agent 无法看到进度 |
| ❌ 删除其他 Agent 的锁文件 | 除非明确过期 |
| ❌ 批量完成多个任务 | 难以追踪和回滚 |

## 10. 自测规范 (Self-Verification)

> ⚠️ **铁律**: 能自动验证的结果，**禁止**交给用户手动检查

### 10.1 核心原则

| 原则 | 说明 |
|------|------|
| 🚫 禁止盲交付 | 不得生成文件后直接让用户"打开看看" |
| ✅ 自动验证 | 生成的数据必须通过脚本验证正确性 |
| ✅ 报告结果 | 向用户报告验证通过/失败的具体指标 |
| ✅ 问题定位 | 验证失败时，自行诊断并修复 |

### 10.2 验证清单

根据任务类型，选择对应的验证方法：

#### 10.2.1 解析器输出 (JSON)

```python
# 验证 JSON 结构和数据完整性
import json
data = json.load(open('output.json'))

# 检查关键字段
assert 'events' in data, "Missing 'events' field"
assert len(data['events']) > 0, "No events parsed"

# 检查特定数据（如 meshInfo）
draws = [e for e in data['events'] if e.get('type') == 'draw']
with_mesh = [e for e in draws if e.get('meshInfo', {}).get('vertexBuffers')]
print(f"Draws with VB data: {len(with_mesh)}/{len(draws)}")
```

#### 10.2.2 HTML 报告

```python
# 从 HTML 中提取嵌入的 JSON 数据并验证
import re, json
html = open('report.html', encoding='utf-8').read()
m = re.search(r'const eventPassData = (\{[^;]+\});', html)
data = json.loads(m.group(1))

# 验证事件数据
events = data.get('events', [])
draws = [e for e in events if e.get('type') == 'draw']
with_mesh = [e for e in draws if e.get('meshData', {}).get('vertexBuffers')]
print(f"HTML Draw events with meshData: {len(with_mesh)}/{len(draws)}")
```

#### 10.2.3 Python 语法

```bash
py -3 -m py_compile <file.py>
echo "Syntax OK"
```

### 10.3 验证报告格式

验证完成后，向用户报告：

```
=== 自动验证结果 ===
✅ JSON 语法: 有效
✅ Events: 180 个事件解析成功
✅ Draw calls: 136 个 (其中 134 个含 VB 数据)
✅ meshData 字段: 已正确转换并嵌入 HTML
⚠️ 注意: 2 个 Draw 无 VB 数据 (可能是 indirect draw)

验证通过，可以交付。
```

### 10.4 验证失败处理

1. **定位问题**: 使用脚本找出具体哪个环节出错
2. **诊断原因**: 检查数据流中断点
3. **自行修复**: 修改代码并重新验证
4. **循环验证**: 修复后必须再次运行全部验证
5. **记录问题**: 在任务文件中记录遇到的问题和解决方案

### 10.5 不可自动验证的情况

某些情况无法完全自动验证，需要说明：

| 情况 | 处理方式 |
|------|----------|
| UI 样式/布局 | 提供截图位置，请用户确认 |
| 性能/响应速度 | 说明测试环境和预期指标 |
| 用户体验 | 列出需要用户确认的交互点 |

**示例**:
```
=== 需用户确认 ===
以下项目无法自动验证，请手动检查：
1. [ ] Mesh Info 选项卡的表格布局是否正确
2. [ ] 点击 Draw 事件后切换到 Mesh Info 选项卡
3. [ ] 确认 VB/IB 数据显示格式符合预期

报告位置: D:\...\mesh_report_final.html
```

## 11. 任务评分规范 (Task Review & Scoring)

> ⚠️ **强制**: 每个任务完成后必须进行评分和评价
> 
> 📋 **核心规则**:
> - 评分记录存放在独立目录 `reviews/`
> - 任务看板只索引评分，不内嵌详情
> - **禁止自评**：Agent 不能评审自己完成的任务

### 11.0 评分文档结构

```
.ai/
├── reviews/                    # 评分文档目录
│   ├── PENDING.md              # 待评分任务队列
│   ├── 2026-01-19.md           # 按日期的评分记录
│   └── ...
```

### 11.1 任务完成 → 自动添加待评分

Agent 完成任务后，**必须**在 `reviews/PENDING.md` 添加待评分记录：

```markdown
### [TASK-XXX] 任务标题
- **完成者**: Echo-0119
- **完成时间**: 2026-01-19 16:30
- **修改文件**:
  - `parse_rdc_xml.py` (+120/-5 行)
- **Commit**: `feat(parser): add mesh info extraction`
- **自评摘要**: 
  - 完成了 Mesh Info 解析功能
  - 遇到字段名不匹配问题，添加了转换函数
- **评分状态**: 🟡 待认领
- **评审者**: -
```

### 11.2 评分认领规则

| 规则 | 说明 |
|------|------|
| 🚫 **禁止自评** | 完成者不能评审自己的任务 |
| ✅ **他评** | 由其他 Agent 认领评分任务 |
| ✅ **标注评审者** | 认领后填写评审者名字 |

**认领流程**:
```
1. 检查 PENDING.md 中的待评分任务
      ↓
2. 确认不是自己完成的任务
      ↓
3. 将"评分状态"改为 🔴 进行中
      ↓
4. 填写"评审者"字段
      ↓
5. 进行评审
```

### 11.3 评分维度与权重

| 维度 | 权重 | 评估内容 |
|------|------|----------|
| **代码质量** | 40% | 语法正确、结构清晰、注释完整、边界处理 |
| **测试验证** | 30% | 自动验证、E2E 测试、边界测试 |
| **文档同步** | 20% | CHANGELOG/INDEX/注释 同步更新 |
| **效率** | 10% | 预估 vs 实际工时 |

**加权计算**:
```
总分 = 代码质量×0.4 + 测试验证×0.3 + 文档同步×0.2 + 效率×0.1
```

### 11.4 评分等级与处理

| 分数 | 等级 | 处理 |
|------|------|------|
| 4.0 - 5.0 | ✅ 优秀 | 归档到 `reviews/YYYY-MM-DD.md` |
| 3.5 - 3.9 | ⚠️ 良好 | 归档，记录改进点 |
| < 3.5 | 🔴 **需返工** | 移到"需返工"区域 |

### 11.5 返工流程

当评分 **< 3.5** 时：

```
1. 评审者标记任务为 🔴 需返工
      ↓
2. 在 reviews/YYYY-MM-DD.md 的"需返工"区域记录：
   - 返工原因
   - 需要改进的具体点
      ↓
3. 任务回到任务看板的"待认领"状态
      ↓
4. 可由原完成者或其他 Agent 认领返工
      ↓
5. 返工完成后，重新进入待评分队列
```

**返工任务标记**:
```markdown
### [TASK-XXX] 任务标题 🔴 返工
- **原完成者**: Echo-0119
- **评审者**: Nova-0119
- **评分**: 3.2 (不通过)
- **返工原因**: 
  - 缺少必要的错误处理
  - 未更新 CHANGELOG
- **返工状态**: 🟡 待认领
```

### 11.6 评分完成后归档

评审完成后，将记录从 `PENDING.md` 移动到 `reviews/YYYY-MM-DD.md`：

```markdown
### [TASK-XXX] 任务标题 ✅
- **完成者**: Echo-0119
- **完成时间**: 16:30
- **评审者**: Nova-0119
- **评审时间**: 17:00

#### 评分详情

| 维度 | 分数 | 说明 |
|------|------|------|
| 代码质量 (40%) | 4.0 | 结构清晰，注释完整 |
| 测试验证 (30%) | 3.5 | 自动验证通过 |
| 文档同步 (20%) | 5.0 | 已同步更新 |
| 效率 (10%) | 4.0 | 预估 30 分钟，实际 35 分钟 |
| **加权总分** | **4.05** | ✅ 通过 |

#### 评审意见
- **优点**: 代码结构清晰
- **改进点**: 建议增加边界测试
```

### 11.7 每日评审任务

每日工作结束时，需要有一个 Agent 认领"每日评审任务"来汇总当日评审：

```markdown
### REVIEW-2026-01-19: 每日评审汇总
- **评审者**: Nova-0119
- **任务数**: 今日完成 3 个任务
- **评审完成**: 3/3
- **平均分**: 4.1
- **返工数**: 0
```
