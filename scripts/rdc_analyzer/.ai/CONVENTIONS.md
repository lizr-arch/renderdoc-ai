# 多 AI 协同开发规范

> **版本**: 1.2.0 | **最后更新**: 2026-01-19
>
> ⚠️ **强制遵守**: 所有参与开发的 AI Agent 必须遵守本规范

## 0. Agent ID 规则

每个 AI Agent 必须使用唯一标识符，格式：

```
Agent-YYYYMMDD-HHmmss
```

**示例**: `Agent-20250119-153000`

**生成规则**:
- 使用会话开始时的时间戳（精确到秒）
- 时区: 本地时间（北京时间 UTC+8）
- 此 ID 用于锁文件、CHANGELOG、任务认领等所有场景

**如何获取当前时间**:
```python
from datetime import datetime
agent_id = f"Agent-{datetime.now().strftime('%Y%m%d-%H%M%S')}"
```

## 0.5 时间获取规范

> ⚠️ **铁律**: AI Agent 没有内置时钟，**禁止**猜测或沿用上下文中的时间

### 0.5.1 核心原则

| 原则 | 说明 |
|------|------|
| 🚫 禁止猜测 | 不得根据"常识"或"记忆"推断当前时间 |
| 🚫 禁止继承 | 不得直接复用上下文/历史消息中的时间戳 |
| ✅ 必须验证 | 每次需要时间时，必须通过系统命令获取 |
| ✅ 一次获取 | 每个会话开始时获取一次，后续复用该时间基准 |

### 0.5.2 标准获取方法

**Windows (CMD/PowerShell)**:
```cmd
echo %date% %time%
```

**跨平台 Python**（推荐）:
```bash
py -3 -c "from datetime import datetime; print(datetime.now().strftime('%Y-%m-%d %H:%M:%S'))"
```

**输出示例**: `2026-01-19 15:40:31`

### 0.5.3 会话时间基准

每个会话开始时，Agent 应：

1. **执行时间获取命令**（上述任一方法）
2. **记录为会话基准时间**
3. **后续操作基于此时间**（如 Agent ID、文件名、时间戳）

```
┌─────────────────────────────────────────────────────────┐
│ 会话开始                                                │
│    ↓                                                   │
│ py -3 -c "..."  →  获得 "2026-01-19 15:40:31"          │
│    ↓                                                   │
│ 记录: SESSION_TIME = "2026-01-19 15:40:31"             │
│    ↓                                                   │
│ Agent ID: Agent-20260119-154031                        │
│ 文件名:   tasks/2026-01-19.md                          │
│ 时间戳:   2026-01-19T15:40:31                          │
└─────────────────────────────────────────────────────────┘
```

### 0.5.4 时间格式标准

| 用途 | 格式 | 示例 |
|------|------|------|
| Agent ID | `YYYYMMDD-HHmmss` | `20260119-154031` |
| 文件名 | `YYYY-MM-DD` | `2026-01-19` |
| 文档时间戳 | `YYYY-MM-DD HH:mm` | `2026-01-19 15:40` |
| ISO 格式 (锁文件) | `YYYY-MM-DDTHH:mm:ssZ` | `2026-01-19T15:40:31Z` |
| CHANGELOG 记录 | `HH:mm` | `15:40` |

### 0.5.5 常见错误及修正

| ❌ 错误做法 | ✅ 正确做法 |
|-------------|-------------|
| 沿用压缩上下文中的 `2025-01-19` | 执行 `echo %date%` 获取真实日期 |
| 假设"今天是 2025 年" | 验证系统时钟后再使用 |
| 文件名写 `2025` 内容写 `2026` | 统一使用获取到的时间 |
| 凭记忆写"下午 3 点" | 使用 `%time%` 获取精确时间 |

### 0.5.6 时间不一致的修复

如果发现现有文件中的时间不一致（如文件名年份与内容年份不符）：

1. **获取当前真实时间**
2. **确定正确年份**（以系统时钟为准）
3. **统一修正**（文件名 + 内容）
4. **Git 提交说明**: `fix(ai): correct timestamp inconsistency`

## 1. 会话启动协议

每个 AI 会话开始时，**必须**执行以下步骤：

```
┌─────────────────────────────────────────────────┐
│ 1. 读取 .ai/INDEX.md      → 了解项目架构         │
│ 2. 读取 .ai/TASKS.md      → 查看任务状态         │
│ 3. 检查 .ai/locks/        → 确认哪些任务被锁定   │
│ 4. 向用户确认             → 明确本次会话目标     │
└─────────────────────────────────────────────────┘
```

**示例开场白**：
```
我已阅读项目索引和任务看板。当前状态：
- 待认领任务: 6 个
- 进行中任务: 0 个

请问您希望我处理哪个任务？或者有新的需求？
```

## 2. 任务认领协议

### 2.1 认领前检查

```bash
# 检查锁文件是否存在
ls .ai/locks/TASK-xxx.lock
```

- ✅ 锁文件不存在 → 可以认领
- ❌ 锁文件存在且未过期 → 不可认领，选择其他任务
- ⚠️ 锁文件存在但已过期（>2小时）→ 可以接管，需在 TASKS.md 中说明

### 2.2 认领步骤

1. **创建锁文件**:
```json
// .ai/locks/TASK-001.lock
{
  "task_id": "TASK-001",
  "claimed_by": "Agent-A",
  "session_id": "会话标识或时间戳",
  "claimed_at": "2025-01-19T15:30:00Z",
  "expires_at": "2025-01-19T17:30:00Z"
}
```

2. **更新 TASKS.md**:
   - 将任务从"待认领"移到"进行中"
   - 填写认领者、时间、预计完成时间

3. **Git 提交**:
```bash
git add .ai/locks/TASK-001.lock .ai/TASKS.md
git commit -m "chore(ai): claim TASK-001 - Pipeline 选项卡数据解析"
```

## 3. 开发过程协议

### 3.1 代码修改规则

| 规则 | 说明 |
|------|------|
| 单一职责 | 每次只修改与当前任务相关的文件 |
| 增量提交 | 每完成一个小功能点立即 commit |
| 保持兼容 | 不破坏现有功能 |
| 添加注释 | 复杂逻辑必须添加注释 |

### 3.2 代码风格

**Python**:
- 缩进: 4 空格
- 编码: UTF-8
- 行宽: 100 字符
- 命名: snake_case (函数/变量), PascalCase (类)

**提交信息** (Conventional Commits):
```
<type>(<scope>): <简短描述>

<详细说明>

<关联任务>
```

类型:
- `feat`: 新功能
- `fix`: 修复 Bug
- `refactor`: 重构
- `docs`: 文档
- `chore`: 构建/工具

**示例**:
```
feat(parser): 添加 Pipeline State 解析

- 解析 RSSetViewports 获取 Viewport 数据
- 解析 OMSetBlendState 获取混合状态
- 支持 D3D11 和 Vulkan 两种 API

Task: TASK-001
```

### 3.3 进度更新

开发过程中，每完成一个验收标准，更新 TASKS.md:

```markdown
### TASK-001: Pipeline 选项卡数据解析
- **进度**: 
  - [x] 分析 relatedCalls 结构
  - [x] 实现 viewport 解析
  - [ ] 实现 blendState 解析  ← 当前进度
  - [ ] 测试 D3D11
```

## 4. 任务完成协议

### 4.1 完成检查清单

- [ ] 所有验收标准已满足
- [ ] 代码已提交到 Git
- [ ] 运行 E2E 测试通过
- [ ] 更新相关文档

### 4.2 完成步骤

1. **最终代码提交**:
```bash
git add <修改的文件>
git commit -m "feat(xxx): 完成 TASK-001"
```

2. **更新 TASKS.md**:
   - 将任务移到"已完成"区域
   - 填写完成时间、产出、测试结果

3. **更新 CHANGELOG.md**:
```markdown
## 2025-01-19

### Agent-A (会话 xxx)
- **15:45** TASK-001: 完成 Pipeline 选项卡数据解析
  - 修改: `parse_rdc_xml.py` (+45 行), `generate_real_report.py` (+20 行)
  - Commit: `feat(parser): add pipeline state extraction`
```

4. **删除锁文件**:
```bash
rm .ai/locks/TASK-001.lock
git add -A .ai/
git commit -m "chore(ai): complete TASK-001"
```

## 5. 冲突处理协议

### 5.1 文件冲突

如果发现要修改的文件被其他任务锁定：

1. **停止修改**
2. **检查锁文件** 确认是哪个任务
3. **评估依赖** 是否需要等待
4. **通知用户** 说明冲突情况

### 5.2 任务依赖

如果任务有依赖关系：

```markdown
### TASK-004: Pipeline State 脚本集成
- **依赖**: TASK-001
```

必须等待 TASK-001 完成后才能开始 TASK-004。

### 5.3 接管过期任务

锁文件超过 2 小时视为过期，可以接管：

1. 删除旧锁文件
2. 创建新锁文件
3. 在 TASKS.md 中说明接管原因

## 8. 禁止行为

| 禁止行为 | 原因 |
|----------|------|
| ❌ 不读取 INDEX.md 直接开发 | 可能重复实现或破坏现有功能 |
| ❌ 不检查锁文件直接认领 | 导致多人同时修改同一文件 |
| ❌ 修改非任务相关文件 | 可能与其他任务冲突 |
| ❌ 不提交 Git 就完成任务 | 其他 Agent 无法看到进度 |
| ❌ 删除其他 Agent 的锁文件 | 除非明确过期 |
| ❌ 批量完成多个任务 | 难以追踪和回滚 |

## 9. 任务文件结构

### 9.1 目录结构

```
.ai/
├── INDEX.md              # 项目索引（AI 必读）
├── TASK_INDEX.md         # 📋 任务总索引（入口）
├── CONVENTIONS.md        # 开发规范（本文件）

│
├── tasks/                # 每日任务文件
│   ├── TEMPLATE.md       # 任务模板
│   ├── 2026-01-19.md     # 按日期存放

│

│
└── locks/                # 任务锁文件
    └── TASK-xxx.lock
```

### 9.2 任务查找流程

```
1. 打开 TASK_INDEX.md
      ↓
2. 找到"当前活跃"表格
      ↓
3. 点击对应日期的任务文件链接
```

1. 复制 `tasks/TEMPLATE.md` 为 `tasks/YYYY-MM-DD.md`
2. 更新 `TASK_INDEX.md` 的"当前活跃"表格
3. Git 提交: `chore(ai): create task file for YYYY-MM-DD`

每月结束时：
1. 将已完成任务汇总到 `archive/YYYY-MM.md`

## 10. 自测规范 (Self-Verification)

> ⚠️ **铁律**: 能自动验证的结果，**禁止**交给用户手动检查

### 10.1 核心原则

| 原则 | 说明 |
|------|------|
| 🚫 禁止盲交付 | 不得生成文件后直接让用户"打开看看" |
| ✅ 自动验证 | 生成的数据必须通过脚本验证正确性 |
| ✅ 报告结果 | 向用户报告验证通过/失败的具体指标 |
| ✅ 问题定位 | 验证失败时，自行诊断并修复 |

### 10.2 验证清单

根据任务类型，选择对应的验证方法：

#### 10.2.1 解析器输出 (JSON)

```python
# 验证 JSON 结构和数据完整性
import json
data = json.load(open('output.json'))

# 检查关键字段
assert 'events' in data, "Missing 'events' field"
assert len(data['events']) > 0, "No events parsed"

# 检查特定数据（如 meshInfo）
draws = [e for e in data['events'] if e.get('type') == 'draw']
with_mesh = [e for e in draws if e.get('meshInfo', {}).get('vertexBuffers')]
print(f"Draws with VB data: {len(with_mesh)}/{len(draws)}")
```

#### 10.2.2 HTML 报告

```python
# 从 HTML 中提取嵌入的 JSON 数据并验证
import re, json
html = open('report.html', encoding='utf-8').read()
m = re.search(r'const eventPassData = (\{[^;]+\});', html)
data = json.loads(m.group(1))

# 验证事件数据
events = data.get('events', [])
draws = [e for e in events if e.get('type') == 'draw']
with_mesh = [e for e in draws if e.get('meshData', {}).get('vertexBuffers')]
print(f"HTML Draw events with meshData: {len(with_mesh)}/{len(draws)}")
```

#### 10.2.3 Python 语法

```bash
py -3 -m py_compile <file.py>
echo "Syntax OK"
```

### 10.3 验证报告格式

验证完成后，向用户报告：

```
=== 自动验证结果 ===
✅ JSON 语法: 有效
✅ Events: 180 个事件解析成功
✅ Draw calls: 136 个 (其中 134 个含 VB 数据)
✅ meshData 字段: 已正确转换并嵌入 HTML
⚠️ 注意: 2 个 Draw 无 VB 数据 (可能是 indirect draw)

验证通过，可以交付。
```

### 10.4 验证失败处理

1. **定位问题**: 使用脚本找出具体哪个环节出错
2. **诊断原因**: 检查数据流中断点
3. **自行修复**: 修改代码并重新验证
4. **循环验证**: 修复后必须再次运行全部验证
5. **记录问题**: 在任务文件中记录遇到的问题和解决方案

### 10.5 不可自动验证的情况

某些情况无法完全自动验证，需要说明：

| 情况 | 处理方式 |
|------|----------|
| UI 样式/布局 | 提供截图位置，请用户确认 |
| 性能/响应速度 | 说明测试环境和预期指标 |
| 用户体验 | 列出需要用户确认的交互点 |

**示例**:
```
=== 需用户确认 ===
以下项目无法自动验证，请手动检查：
1. [ ] Mesh Info 选项卡的表格布局是否正确
2. [ ] 点击 Draw 事件后切换到 Mesh Info 选项卡
3. [ ] 确认 VB/IB 数据显示格式符合预期

报告位置: D:\...\mesh_report_final.html
```

## 11. 任务评分规范 (Task Review & Scoring)

> ⚠️ **强制**: 每个任务完成后必须进行评分和评价
> 
> 📋 **评审任务**: 每日评审本身是一个**独立任务**，需要 AI 认领和完成

### 11.0 评审任务定义

**每日评审**是一个特殊的任务类型，编号格式：`REVIEW-YYYY-MM-DD`

```markdown
### REVIEW-2026-01-19: 每日评审任务
- **类型**: 📊 评审任务 (Review)
- **优先级**: P0 (每日最后必须完成)
- **前置条件**: 当日所有开发任务完成或结束
- **验收标准**:
  - [ ] 每个已完成任务有评分和评价
  - [ ] 填写每日汇总评分表
  - [ ] 撰写今日总结（做得好/需改进/明日计划）
  - [ ] 更新 CHANGELOG.md
```

**认领规则**:
- 每日工作结束前，**必须**有一个 Agent 认领 `REVIEW-YYYY-MM-DD`
- 评审任务**不计入**开发任务统计
- 评审任务完成后，**不需要**被评审（自审任务）

**锁文件示例**:
```json
// .ai/locks/REVIEW-2026-01-19.lock
{
  "task_id": "REVIEW-2026-01-19",
  "claimed_by": "Agent-20260119-153000",
  "claimed_at": "2026-01-19T17:30:00Z",
  "type": "review"
}
```

### 11.1 单任务评分

任务完成后，在"已完成"区域填写：

```markdown
### TASK-XXX: 任务标题 ✅
- **完成者**: Agent-XXXXXXXX-XXXXXX
- **完成时间**: HH:MM
- **实际工时**: XX 分钟
- **评分**: ⭐⭐⭐⭐☆ (4/5)
- **评价**:
  - 代码质量: 良好
  - 测试覆盖: 完整
  - 文档更新: 已更新
- **产出**:
  - 修改: `parse_rdc_xml.py` (+120/-5 行)
  - Commit: `feat(parser): add mesh info extraction`
- **问题与经验**:
  - 问题: JSON 字段名不匹配，导致 HTML 渲染失败
  - 解决: 添加 convert_mesh_info_to_mesh_data 转换函数
  - 经验: 修改解析器后需重新生成 JSON 数据
```

### 11.2 评分维度

| 维度 | 评估内容 | 评分标准 |
|------|----------|----------|
| **代码质量** | 语法正确、结构清晰、注释完整 | 优秀/良好/一般/较差 |
| **测试覆盖** | 自动验证、边界测试、E2E 测试 | 完整/部分/缺失 |
| **文档更新** | INDEX/CHANGELOG/注释同步 | 已更新/未更新/无需更新 |
| **效率** | 预估 vs 实际工时 | 提前/准时/超时 |

每日工作结束时，填写"今日 Review & 评分汇总"：

| 维度 | 评分 (1-5) | 说明 |
